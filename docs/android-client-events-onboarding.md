# Client service events and native registration

This release adds Android client 0.2.0 and driver 0.4.0. Both have native account creation, explicit email confirmation guidance, resend confirmation and password recovery. Recovery returns to the existing production web origin, presents a dedicated new-password screen, then locally signs out that browser recovery session. The apps never persist signup passwords or silently use a signup response as a session. Verify production email confirmation and recovery redirect settings with a real user-initiated email test.

New driver signups are pending regardless of editable Auth metadata. Existing accounts retain approved pilot access. Restrictive RLS intersects all current jobs/location/notification/device policies so older clients cannot bypass approval. A trigger prevents self-approval. The administrator web panel can review pending accounts, approve/reject with a note, and records an immutable audit. Name, phone, supported vehicle and plates are required to approve. Document collection/upload is a separate pending stage; this pilot review is not automated identity, licensing or insurance verification.

Client events are emitted by database inserts/transitions: requested, assigned, driver-arrived-at-pickup, picked-up, driver-arrived-at-delivery, completed, cancelled and released/reassignment. Arrivals are explicit driver confirmations, row-locked against release/completion, server-timestamped and idempotent within an assignment cycle. Every event remains in the client's own paginated notice history. Public clients cannot manufacture event rows or rewrite their contents.

FCM uses separate client devices and private outbox, with the existing server-only Firebase credential and private Vault hook. Eligibility checks client role, current ownership, live Auth session, local installation/user/login nonce and notification permission. Device invalidation matches token and nonce exactly. Messages have no address, price or personal details. A newer queued event supersedes an older push for the same job to avoid announcing obsolete states after an outage; the notice history retains every transition. Android delivery still depends on platform/network/notification settings and requires physical device acceptance.

The optional release helper can provision only `app.fletya.client` within Firebase project `fletya`. It requires the existing private server hook, keeps Google OAuth/private keys server-side, and returns only public google-services configuration. If its existing service account lacks Firebase Management permission, obtain the public configuration by registering that exact Android package in the Firebase console; do not grant broader roles or share private keys to work around a failure. Client production push is enabled in a build only when matching public Firebase configuration exists. Test flavor push remains disabled.

Validation includes native registration/recovery/push nonce tests, web password recovery and pending-driver checks, FCM HTTP tests, rollback/disposable RLS/events/approval tests, live project advisor comparison, Android unit/lint/APK CI, and existing service/security regressions. Existing driver locked-screen push acceptance remains deferred. Pricing and payment processing are separate future work.
